## Pipeline Efficiency X Goal Completion PArt II

Making a decision on whether to spend time automating a set of tasks or checking off the tasks one-by-one is difficult. If you “just do it” (Not sponsored by Nike), you can get them out of the way quickly. If you choose to take the time and optimize the process, it will be sluggish, and you might not even get to any of the tasks right away. But which is best? Sounds like an easy answer. 

Most people just do it, and yes, this may be the best way sometimes, but then when should automation and optimization be taken into account?

To me a good rule of thumb is frequency. Once you realize that task/s is/are done frequently we can check complexity: how many tasks is this workflow composed of? Lastly but maybe closely related to frequency is the project horizon— how long is the project? Some might be life long projects others; one-and-done and are so infrequent you may not want to worry about. 

This Blog for example started as just a small practice exercise on writing. As a musician, I can guarantee you that a skill you don’t practice is a skill you will gradually lose. 

So the frequency is meant to be sporadic with a vanishing horizon and a healthy size workflow that grows as I learn. When I started, the idea was to also explore a few technological tools, and frameworks. I already talked about github as a host and jekyll as an engine in a different [blog](https://jeffbr96.github.io/jbc.github.io/jekyll/github/automation/2025/11/22/blog-3.html). These technologies do a lot of work in the background to serve what you are reading. In the Software Engineering world we call this abstraction. 

We abstract away the things that are fundamental—sometimes through inheritance—and things that are parallel because we want to focus on the task at hand. We encapsulate these parallel parts so we safeguard all processes by ensuring rules and controlling accessibility. We also encourage reusability by abstracting: this way, we build the wheel only once. We can promote polymorphism to reduce duplication, and extend or override if necessary—this is off-topic here; I think I wrote quite a bit about OOP (Object Oriented Programming) in my undergrad years.

So, choosing and using a framework is a first form of pipelining, or maybe choosing the pipes. One of the first technologies I wanted to try was using LLM CLI (Large Language Model; Command Line Interface) as a project assistant. I wanted to try that after watching this YouTube [video](https://www.youtube.com/watch?v=MsQACpcuTkU&t=1877s). If you are into tech, you should watch it. It is a whole topic, and I won't get into it here. In a nutshell, it can read and write files in a folder or project and is extremely helpful—sometimes not. I will probably write about my experience using LLMs separately. To do this I had to read some documentation, and set a few things up, DevOps. 

Choice of operating systems matters and Windows is not the most helpful. Thankfully I had WSL (Windows Subsystem for Linux) installed. This shows how things we learn or do and set up in the past have a surprising way of becoming helpful in the future, which are unforeseen—Oposite of Tech-Debt Tech-Credit, I guess more like Tech-Savings or investment: pick your analogy.    

While working through this project, I started to see a few things I was doing, which would become repetitive in the future. Nothing wrong with repetitive; we want things to be standardized, so work is predictable. And if it is predictable, it can be automated; the more you automate, the greater flexibility you have with the creative parts that can’t and shouldn’t be automated. 

I started with the Social Media Card. I’ll be open to you here: I don't claim to know about Social-Engineering—(insert laugh emoji here) that’s more like DevSec—just a play on words, this should be more like Social-Media-Engineering. 
[A million dollar idea, tech consultancy for influencers: you can use it, I’ll only take 3%.]

So, since I’m not too savvy on web development, this is also a learning experience. A Social Media Card is something that is embedded in the HTML. Social Networks use this to render how you see something when you share a link. The meta tags are standard, and anyone can add them. 

Jekyll engine would create these meta tags automatically when the config part of the blog has the address for the image to be used. I didn’t want just the background image to be used, so I decided to use the abstract/excerpt to display some portion of the text. Doing this over and over again is time-consuming. That’s not what this project was about. I would have to do it for every blog—so maybe a lot, or maybe not. 

I decided to automate that. Using Python and a few image-editing libraries I created a program to resize the background image, find the excerpt and write on the image, and save it as a separate image just for the media card in the appropriate folder. 

When I tried it out, I realized that the font looked wonky, because a small number of words needed a bigger font, and a large number of words should have a smaller font. I automated the size of the font by word count using five discrete sizes per some defined word count. I learned a few things and now this frees up time because when I’m ready I just run the script and a social card is built for me.
